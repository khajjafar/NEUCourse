# Firestore Data Model — NEUCourse

This document describes every Firestore collection and document used by NEUCourse,
the fields stored in each, their types, and the access rules that protect them.

---

## Firebase Project Configuration

### Environment Variables

| Variable | Where used | Description |
|---|---|---|
| `NEXT_PUBLIC_FIREBASE_API_KEY` | Client | Firebase web API key |
| `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN` | Client | e.g. `<project>.firebaseapp.com` |
| `NEXT_PUBLIC_FIREBASE_PROJECT_ID` | Client + Server | Project ID (shared) |
| `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET` | Client | Storage bucket (unused at runtime) |
| `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID` | Client | Cloud Messaging sender |
| `NEXT_PUBLIC_FIREBASE_APP_ID` | Client | App registration ID |
| `FIREBASE_CLIENT_EMAIL` | Server only | Service account email |
| `FIREBASE_PRIVATE_KEY` | Server only | Service account private key (newlines as `\n`) |

**Never commit `.env.local`.** An `.env.example` with placeholder values should be committed instead.

### SDK Initialisation Pattern

- **Client SDK** (`lib/firebase.ts`) — initialised once via `getApps().length` guard; exports `auth` and `db`.
- **Admin SDK** (`lib/firebase-admin.ts`) — server-only, initialised once via `admin.apps.length` guard; exports `adminDb` and `adminAuth`.
  The Admin SDK is imported only inside `/lib/firebase-admin.ts` and `/app/api/v1/**` route handlers.

### Authentication

Firebase Authentication is enabled with the **Email/Password** provider. JWTs issued by Firebase Auth are verified server-side via `adminAuth.verifyIdToken()` (wrapped in `verifyAuth()` from `lib/api-helpers.ts`) on every authenticated API route.

## Collection Hierarchy

```
users/{userId}
  plans/{planId}
    semesters/{semId}
  events/{eventId}

courses/{courseId}                    ← read-only at runtime; written by scraper only
```

---

## `users/{userId}`

Top-level document representing an authenticated user's profile metadata.
The document ID equals the Firebase Auth UID.

| Field | Type | Required | Description |
|---|---|---|---|
| `requirements` | `RequirementGroup[]` | No | Graduation requirement groups (added by Issue #31 feature) |

### `RequirementGroup` shape

```typescript
{
  id: string;       // e.g. "cs-core"
  name: string;     // e.g. "CS Core Courses"
  count: number;    // number of credits or courses required
}
```

**Notes**
- Document is created lazily on first `PATCH /api/v1/profile` call (uses `set(..., { merge: true })`).
- `GET /api/v1/profile` returns `{}` (empty object) if the document does not yet exist.

---

## `users/{userId}/plans/{planId}`

Degree plan metadata. Document ID is auto-generated by Firestore (`adminDb.collection(...).add(...)`).

| Field | Type | Required | Description |
|---|---|---|---|
| `name` | `string` | Yes | User-chosen plan name, e.g. `"MSCS 2025–2027"` |
| `createdAt` | `Timestamp` | Yes | Server timestamp set on creation |
| `updatedAt` | `Timestamp` | No | Server timestamp, updated on every mutation |

**Notes**
- `createdAt` uses `FieldValue.serverTimestamp()` — never `new Date()`.
- `updatedAt` is written on every PUT/PATCH to the plan and on every course add/remove inside a semester.
- The `GET /api/v1/plans` response augments each plan with a computed `semesterCount` field (not stored in Firestore; derived by counting the `semesters` subcollection).

---

## `users/{userId}/plans/{planId}/semesters/{semId}`

One semester within a degree plan. Document ID is auto-generated.

| Field | Type | Required | Description |
|---|---|---|---|
| `name` | `string` | Yes | Display name, e.g. `"Fall 2025"` |
| `order` | `number` | Yes | Integer sort key; used to order semesters left-to-right in the UI |
| `courses` | `CourseAssignment[]` | Yes | Ordered list of courses in the semester (may be empty `[]`) |

### `CourseAssignment` shape

```typescript
{
  courseId: string;  // matches courses/{courseId} document ID, e.g. "CS3500"
  crn?: string;      // optional — only set when user picked a specific section
}
```

**Notes**
- Courses are stored as an array of objects inside the semester document (not as a subcollection).
- Adding a course uses `FieldValue.arrayUnion(coursePayload)` to avoid race conditions.
- The array is written directly (overwrite) on PATCH to support drag-and-drop reordering.
- Removing a course uses `FieldValue.arrayRemove(coursePayload)` via `DELETE /api/v1/plans/{planId}/semesters/{semId}/courses/{courseId}`.

---

## `users/{userId}/events/{eventId}`

A single calendar event (class block, club meeting, office hours, etc.).
Document ID is auto-generated.

| Field | Type | Required | Description |
|---|---|---|---|
| `title` | `string` | Yes | Event title displayed on the calendar |
| `startTime` | `string` | Yes | ISO 8601 datetime, e.g. `"2025-09-08T10:30:00"` |
| `endTime` | `string` | Yes | ISO 8601 datetime, e.g. `"2025-09-08T11:35:00"` |
| `location` | `string` | No | Room or building; defaults to `""` |
| `color` | `string` | No | Tailwind color name for the event chip; defaults to `"blue"` |
| `createdAt` | `Timestamp` | Yes | Server timestamp set on creation |
| `updatedAt` | `Timestamp` | Yes | Server timestamp, updated on every PUT |

**Notes**
- Events are fetched ordered by `startTime` ascending.
- `startTime` and `endTime` are stored as ISO strings (not Firestore Timestamps) to simplify serialisation over the REST API.
- The weekly calendar detects overlapping events client-side using these string values with `date-fns`.

---

## `courses/{courseId}`

Pre-scraped NEU course catalogue. Written once by `scripts/scrape-courses.ts`; **read-only at runtime**.
Document ID equals the course's `id` field (e.g. `"CS3500"`).

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | `string` | Yes | `"<SUBJECT><NUMBER>"`, e.g. `"CS3500"` |
| `subject` | `string` | Yes | Department code, e.g. `"CS"` |
| `number` | `string` | Yes | Course number, e.g. `"3500"` |
| `name` | `string` | Yes | Full course title |
| `description` | `string` | Yes | Catalogue description |
| `creditHours` | `number` | Yes | Credit hours |
| `prereqs` | `string[]` | Yes | List of prerequisite course IDs (may be `[]`) |
| `coreqs` | `string[]` | Yes | List of co-requisite course IDs (may be `[]`) |
| `sections` | `ClassSection[]` | Yes | Available sections (may be `[]`) |

### `ClassSection` shape

```typescript
{
  crn: string;           // Course Registration Number
  seats: string;         // Available seats (as string from scraper)
  meetingTimes: string;  // Raw string, e.g. "MWF 10:30am–11:35am"
  rooms: string;         // Location, e.g. "West Village H 110"
  professor: string;     // Instructor name
  campus: string;        // e.g. "Boston"
}
```

**Important notes on `meetingTimes`**:
- Scraped from SearchNEU; may contain an en-dash (`–`) as the time separator instead of a hyphen.
- `lib/parse-meeting-times.ts` normalises this before parsing.

**Access**:
- `GET /api/v1/courses` — public, no auth required; results cached in-memory for 1 hour.
- `GET /api/v1/courses/{courseId}` — public, no auth required.
- Write access: scraper only (local script, not a cloud function).

## Firestore Security Rules

```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // Users can read and write only their own profile document
    match /users/{userId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;

      // Users can read and write only their own plans and semesters
      match /plans/{planId} {
        allow read, write: if request.auth != null && request.auth.uid == userId;

        match /semesters/{semId} {
          allow read, write: if request.auth != null && request.auth.uid == userId;
        }
      }

      // Users can read and write only their own events
      match /events/{eventId} {
        allow read, write: if request.auth != null && request.auth.uid == userId;
      }
    }

    // Courses collection is readable by all authenticated users; not writable at runtime
    match /courses/{courseId} {
      allow read: if request.auth != null;
      allow write: if false;
    }
  }
}
```

**Key points**:
- Every document under `users/{userId}` is gated on `request.auth.uid == userId` — users cannot read or write each other's data.
- The `courses` collection is readable by any authenticated user (needed for course search and plan building).
- `courses` write access is denied at the rules level; only the Admin SDK (bypasses rules) can write during the scrape.
- Unauthenticated clients have no read access to any collection.

## Access Pattern Summary

| Collection | Who reads | Who writes | Auth required |
|---|---|---|---|
| `users/{userId}` | Owner only | Owner only | Yes — JWT + UID match |
| `users/{userId}/plans/{planId}` | Owner only | Owner only | Yes — JWT + UID match |
| `users/{userId}/plans/{planId}/semesters/{semId}` | Owner only | Owner only | Yes — JWT + UID match |
| `users/{userId}/events/{eventId}` | Owner only | Owner only | Yes — JWT + UID match |
| `courses/{courseId}` | Any authenticated user | Scraper (Admin SDK) only | Read: Yes; Write: Admin SDK bypasses rules |

All runtime reads and writes go through the Next.js API routes under `/app/api/v1/` — client components never call Firestore directly.
